# freshon-admin-1 운영지도 이전

이 문서는 후보 브랜치에서의 전환 절차를 기록한다. 적용 대상은 Render 서비스 `srv-d87gc5rtqb8s7398t37g`와 `https://freshon-admin-1.onrender.com`이다. 기존 Stage는 `srv-da47hugu01pc73etpfa0`이다. 2026년 12월의 무료 대역폭 갱신과 사용자 배포 승인을 확인한 뒤에 진행한다.

## 배포 전 확인

1. Render Dashboard에서 이번 사용 주기의 무료 잔량과 예상 송신량을 확인한다. 한도 안에 검증과 즉시 롤백을 모두 수행할 여유가 있어야 한다. Stage 배포를 만들지 않는다.
2. `scripts/audit-opsmap-primary-preservation.mjs`를 승인된 읽기 인증으로 실행한다. 작업 브랜치를 만든 시점에 기존 공인 기준호차 4,434곳은 대조됐고, 기존 보존 스냅샷 5,698행 중 375곳은 현재 전국 등록 원장에 연결되지 않았다. 375곳은 기존 보존본에 남아 있다. 2026-11-25 FreshOn 고객사정보현황에서 375곳을 고객코드별로 대조했다. 오산 현재 등록 374곳은 Stage 등록 원장에만 추가하는 별도 암호화 복구본으로 준비했다. 거래 종료 확인은 0곳이다. 사용 안 함 1곳은 종료 근거가 없어 기존 보존본에만 유지한다. 복구본의 정식 반영과 미확인 건의 보존 근거를 다시 확인하기 전까지 `ready: false`를 유지한다. 감사용 출력만 변경하거나 기존 보존 스냅샷을 축소해 통과시키지 않는다.
3. 지급된 실제 원장 버전과 SHA를 확인한다. `stage/opsmap-snapshots`에는 기준호차·등록·배송이력·우편번호 자료가, `stage/opsmap-wms-exports`에는 검증된 WMS 자료가 유지된다. 기존 본서버의 스냅샷·직원 인증·수동 핀 및 Stage 수동 핀은 별도 비공개 브랜치의 현재 커밋으로 보존한다. 최초 감사에서는 양쪽 원장의 유효한 수동 핀 1건이 고객코드, 주소 해시, 좌표까지 일치했다. 이후 일치하지 않는 Stage 수동 핀이 생기면 승인된 정정 절차로 반영 대상을 확정한 뒤 감사를 다시 실행한다. 읽기 전용 감사 결과의 `evidence`와 그 JSON 본문의 SHA-256을 승인 자료로 사용한다. 키·토큰·원본 자료는 GitHub 소스와 작업 로그에 저장하지 않는다.
4. 기존 본서버 직원 인증·수동 핀 저장소·납품사진·도로경로/주소 호출량 원장을 확인한다. 본서버 직원 세션과 Production 예산 원장을 유지한다. 암호화 자료를 읽을 때 승인된 기존 복호화 키를 사용한다. `OPSMAP_PRIMARY_ARCHIVE_READ_TOKEN`은 원장 읽기 전용, `OPSMAP_PRIMARY_ARCHIVE_WRITE_TOKEN`은 검증된 원장 게시용으로 구분한다.
5. `OPSMAP_PRIMARY_CUTOVER_APPROVED`, `OPSMAP_PRIMARY_PRESERVATION_JSON`, `OPSMAP_PRIMARY_PRESERVATION_SHA256`은 올바른 운영 서비스와 감사 결과에만 연결한다. 먼저 `OPSMAP_PRIMARY_SYNC_OWNER`를 비활성으로 유지하고 읽기만 검증한다. 기존 Production LIVE `5b73b0cc360416ddaf70d155ac4c9fa8522e0f0b`의 Render 배포 ID를 확인해 롤백 기준으로 기록한다.

## 오산 고객코드 복구 검증

- 정기 갱신은 이미 승인된 고객코드의 센터와 주소 해시가 일치할 때만 해당 매장을 받는다. 374곳은 모두 현재 등록 게시본 확인 전에 생성됐고 승인된 고객코드 범위 밖이었다.
- Stage 별도 전국 등록 게시본 16,788행을 기준으로 374행만 추가했다. 격리 복구본 17,162행에서 기존 행과 좌표는 유지했다. 기존 본서버 좌표나 호차로 신규 등록을 채우지 않았다.
- 사용 여부와 거래 종료를 구분한다. 사용 중이나 종료일 형식이 올바르지 않은 13곳은 원천의 등록 상태를 유지하고 날짜는 정정 대상으로 남긴다. 사용 안 함 1곳은 종료 상태와 유효한 종료일이 제공될 때에만 종료로 분류한다.
- 배포 승인 이후 실제 게시 전 최신 등록 버전, 중복 고객코드, 센터, 주소를 다시 확인한다. 복구된 코드가 다음 정기 갱신의 승인 범위에 포함되는지도 별도로 확인한다. 코드·주소 상세는 Windows 사용자 암호화 보관본을 사용한다.

## 회귀 판정

실패 7건은 검색 상태와 공간 인덱스가 제공되지 않은 모의 시험 2건, 신규권역 상태값과 권역선 재사용·공동담당 표시의 이전 기대값 3건, 과거 본서버 코드를 기준으로 했던 바이트 대조 2건이었다. 보존해야 할 수집기와 기존 경로는 승인된 Stage 후보 `614441a`의 같은 코드 구간과 대조했다. 직원 화면과 런타임을 수정하지 않고 검증 기준을 정정했다.

## 단일 실행자 전환

1. 승인된 Apps Script 소유자가 기존 프로젝트의 `opsmapStageClockStatus`에서 시계 트리거가 정확히 1개이고 실제 UID와 실행자 해시가 일치하는지 확인한다. 기존 스케줄에서 실행 중인 작업의 최종 영수증과 게시 포인터를 먼저 확인한다.
2. 발송 설정인 `OPSMAP_STAGE_SYNC_DISPATCH_V1`의 기존 Stage 값을 보관하고 `enabled: false`로 잠시 멈춘다. Stage에서 진행 중인 수집과 게시가 종료된 시점에 Stage의 수집 승인 스위치를 해제한다. Stage 정상본과 원장은 그대로 둔다.
3. 동일 Apps Script 프로젝트에 검증된 스크립트와 URL 허용 목록을 적용한다. 기존 실행자와 UID를 그대로 사용한다. 정식 `OPSMAP_PRIMARY_CLOCK_SECRET`을 Script Properties와 본서버의 승인된 보안 설정에 연결한다. 수신 측 UID와 실행자 해시를 각각 `OPSMAP_PRIMARY_CLOCK_TRIGGER_ID`, `OPSMAP_PRIMARY_CLOCK_EXECUTOR_SHA256`에 연결한다. 새 트리거를 설치하지 않는다.
4. 본서버 쓰기 검증을 마친 뒤 `OPSMAP_PRIMARY_SYNC_OWNER=1`과 `OPSMAP_PRIMARY_ARCHIVE_WRITE_APPROVED=1`을 적용한다. 발송 프로필을 `PRIMARY_HOURLY_WMS_V1`으로 맞춘 뒤 한 번만 활성화한다. 같은 서명은 기존 Stage에서 사용할 수 없다. 기존 스케줄 외 시간에는 원천을 호출하지 않는다. 야간 WMS는 다음 날 게시 상태를 확인하고 자정 및 아침 중복 수집을 차단한다.
5. 같은 실행 ID에서 기준호차 Excel·전국 등록·배송이력·WMS·우편번호 결과를 각각 대조한다. 실패 항목은 직전 게시본과 해시를 조회해 보존을 확인한다. 직원 Chrome에서 검색, 주소 주변 핀, 음영권역, 배차 참고, 연락처, 사진, 인증·로그아웃을 확인한다. 도로경로 호출은 유효한 기존 승인이 있는 경우에만 실행한다. 새 지도에서 기존 수동 핀과 사진을 함께 확인한다.
6. 본서버의 첫 무인 정기 실행, 직원 화면, 원장 재조회가 성공한 뒤에만 Stage를 일시 중지한다. Stage를 삭제하지 않는다.

## 원복

- **코드:** Apps Script 발송을 먼저 중지한다. 진행 중인 본서버 쓰기 여부를 확인하고 본서버 쓰기를 끈다. 읽기 전환을 해제하거나 Render에서 기존 `5b73b0c` 배포로 원복한다. 직원 로그인과 지도·원장 조회를 다시 확인한다.
- **데이터:** 코드 원복과 별도로 다룬다. 코드 문제라면 게시 포인터는 유지한다. 실제 데이터 손상이 확인된 항목만 마지막 검증 포인터와 해시를 확인한 뒤 기존 CAS 절차로 복구한다. 비공개 브랜치 자체를 되감거나 정상 원장을 삭제하지 않는다.
- **발송:** 본서버 작업과 쓰기 권한이 비활성화됐음을 확인한다. Stage가 중지됐다면 다시 시작하고 기존 Stage 프로필, UID, 실행자, 서명을 복구한다. 기존 트리거 1개를 재사용한다.

## 송신량 확인

보호 데이터에는 기존 세션 검증과 `private, no-store`를 유지한다. 열린 탭에서 가지고 있는 스냅샷·기준호차 버전이 서버와 같으면 본문 대신 상태만 수신한다. 다른 버전이면 전체 검증 데이터를 받는다. 서버도 보관소의 게시 포인터를 확인하고 동일한 기준호차 버전의 원본을 재다운로드하지 않는다. 새 탭과 로그아웃 이후에는 세션 데이터를 다시 받는다.

본서버 업스트림 송신 2.58GB는 Render 집계로 확인했다. Hub와 비공개 저장소별 송신량은 확인되지 않았다. 이 후보는 중복 좌표 새로고침과 레지스트리 규칙 동시 조회를 합친다. 신규 원장 실행자가 활성화된 경우에는 기존 본서버 스냅샷 자동 작업을 중지한다. 전환 후 동일 사용량 조건에서 Render HTTP 송신과 업스트림 송신을 각각 비교한다.
